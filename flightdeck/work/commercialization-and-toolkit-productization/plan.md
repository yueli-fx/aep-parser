# 计划 — 商业化与 Toolkit 产品化

## 分支 A：用户与问题验证

- 选择一个主 ICP 和一个对照 ICP。
- 使用真实 AEP 样本验证检查、依赖、diff、迁移和批处理痛点。
- 记录当前人工流程、频率、错误成本、预算所有者与采购阻力。

## 分支 B：Toolkit contract

- 收敛公开 Go interface、CLI JSON envelope、错误分类和兼容承诺。
- 定义 inspection、authoring、migration 的稳定性等级，避免实验性写能力污染稳定 interface。
- 为每项公开承诺关联可查询的证据等级。

## 分支 C：集成与交付

- 建立 nexrender/aerender、DAM、CI 和批量目录扫描的参考集成。
- 决定二进制、容器、私有部署或托管 API 的交付组合。
- 建立升级、回滚、数据保留和兼容策略。

## 分支 D：采用与信任

- 完成首个公开版本、示例工程、故障模型和安全说明。
- 用真实设计伙伴结果替代抽象功能列表。
- 建立 issue、兼容性反馈和样本最小化流程。

## 分支 E：商业验证

- 分别测试支持订阅、企业部署、托管 API 和专项迁移服务的付费意愿。
- 按节省的人工检查时间、避免的渲染失败和资产治理规模评价价值。
- 设定继续、调整和停止条件，不以下载量代替付费或生产采用信号。

## 分支 F：长期生态

- 评估格式知识、规则包、插件识别和迁移策略的社区贡献模型。
- 保持开源核心与商业层的数据格式和 extension seam 可互操作。
- 只有出现至少两个真实 adapter 后才抽象新的 port，避免为假想集成增加浅 interface。
